# Issue → Milestone Planner

Plan upcoming minor-version milestones for a GitHub repository so that **every issue lands in a milestone strictly later than the issues it depends on**. The user wants the dependency order preserved: if `A` blocks-on `B` and `B` blocks-on `C`, then `C → v1.2`, `B → v1.3`, `A → v1.4`.

This skill is fully automatic — once the plan is computed it creates milestones and assigns issues without asking again. Do not pause for confirmation unless something is genuinely ambiguous (cycles, missing version, repo not detected).

## When to refuse / pause

Refuse and report instead of guessing if any of these are true:

- Not inside a git repo, or `gh` CLI not authenticated (`gh auth status` fails).
- Current version cannot be detected from any source (see below) — ask the user for it.
- The dependency graph has a **cycle** that includes issues you actually intend to schedule. Report the cycle and stop; do not silently break it.

## The pipeline

Run these steps in order. Each step has a small, verifiable output — print a one-line status after each so the user can follow along.

1. **Verify environment** — `gh auth status` and `git rev-parse --show-toplevel`. Resolve the repo's `owner/name` via `gh repo view --json nameWithOwner -q .nameWithOwner`. Store as `REPO`.
2. **Detect current version** — see *Version detection*.
3. **Fetch open issues** — see *Fetching issues*.
4. **Classify each issue's Type** — assign one of `Bug`, `Feature`, `Task`. See *Issue Type classification*.
5. **Build dependency edges** — combine three sources (body parsing, GitHub native sub-issues, semantic inference). See *Dependency extraction*.
6. **Plan milestones** — feed edges + issue list into `scripts/plan_milestones.py`. See *Planning*.
7. **Show the plan** — one compact table (include Type column), then create milestones, assign issues, and apply Types. See *Execution*.

The user said "fully automatic", so steps 6 → 7 run back-to-back. Still print the plan first so they see what happened.

## Version detection

The next milestones are derived by bumping the current minor and resetting patch:

`v1.1.1 → v1.2 → v1.3 → v1.4 …`  
`v0.4.2 → v0.5 → v0.6 …`

Always use the `vMAJOR.MINOR` format (no patch, no suffix). The user explicitly chose this format — do not switch to `1.2.0` or plain `1.2`.

Resolve the current version in this priority order. Stop at the first source that yields a semver match:

1. `git tag --list 'v*' --sort=-v:refname | head -n1` — parse `vX.Y.Z` (Z optional).
2. `git tag --sort=-v:refname | head -n1` — same, without the `v` filter.
3. `.claude-plugin/plugin.json` → `.version`
4. `package.json` → `.version`
5. `pyproject.toml` → `[project] version` or `[tool.poetry] version`
6. `Cargo.toml` → `[package] version`

If none match, ask the user once: "What's the current version? (e.g., 1.1.1)". Do not invent one.

When parsing, treat missing patch as `0` and ignore any pre-release / build suffix. The next minor sequence is generated by `scripts/plan_milestones.py` — you do not need to compute it inline.

## Fetching issues

```bash
gh issue list --state open --limit 1000 \
  --json number,title,body,labels,milestone,assignees,createdAt,url
```

Save to a temp file (e.g., `/tmp/imp-issues.json`). Two things to note:

- **Skip issues that already have a non-null `milestone`.** The user is iterating on a plan; existing assignments are intentional. If they want a full rebalance they will say so explicitly — handle that by asking once before proceeding.
- **Pull requests are filtered out** automatically by `gh issue list` — no need to check `pull_request` field.

If the issue count is huge (>500) and the user did not ask for "all", confirm scope before continuing.

## Issue Type classification

Every scanned issue must be tagged with exactly one of the GitHub native Issue Types: **`Bug`**, **`Feature`**, or **`Task`**. These are first-class repo-level fields (not labels) introduced by GitHub in 2024 — they appear in the issue header next to the title.

### Decide the Type in this priority order

Stop at the first rule that matches. Compare case-insensitive substrings unless noted.

1. **Existing Type already set** — fetch via GraphQL `issueType { name }`. If the issue already has a non-null Type, keep it. Do not override the maintainer's prior choice.
2. **Labels** (highest signal among heuristics):
   - `bug`, `defect`, `regression`, `crash`, `broken`, `錯誤`, `缺陷` → **Bug**
   - `feature`, `enhancement`, `feat`, `新功能`, `新增功能` → **Feature**
   - `task`, `chore`, `refactor`, `docs`, `documentation`, `cleanup`, `maintenance`, `重構`, `文件`, `雜項` → **Task**
3. **Conventional-commit-style title prefix** (`<type>:` or `<type>(scope):`):
   - `fix:`, `bugfix:`, `hotfix:` → **Bug**
   - `feat:`, `feature:` → **Feature**
   - `chore:`, `refactor:`, `docs:`, `test:`, `build:`, `ci:`, `perf:`, `style:` → **Task**
4. **Title / body keyword scan** (whole-word match where the language has word boundaries):
   - Bug indicators: `fix`, `fixes`, `fixed`, `bug`, `broken`, `error`, `crash`, `regression`, `doesn't work`, `not working`, `fails`, `failing`, `incorrect`, `wrong`, `misbehaves`, `修`, `修復`, `修正`, `錯誤`, `壞`, `失敗`, `異常`
   - Feature indicators: `add`, `support`, `implement`, `introduce`, `new`, `allow`, `enable`, `expose`, `新增`, `加入`, `支援`, `實作`, `提供`, `功能`
   - Task indicators: `refactor`, `cleanup`, `clean up`, `tidy`, `reorganize`, `rename`, `migrate`, `upgrade`, `bump`, `update dependencies`, `docs`, `document`, `documentation`, `test`, `chore`, `重構`, `整理`, `搬移`, `更新`, `升級`, `文件`
5. **Fallback** — if nothing above matches, default to **Task**. Task is the safe catch-all (administrative or unclassified work).

If two categories tie (rare — e.g., title contains both `add` and `fix`), prefer **Bug** over **Feature** over **Task**, because a wrongly-tagged Bug is the most actionable to re-triage.

### Apply the Type

GitHub exposes Type assignment through GraphQL only (no REST endpoint at time of writing). The `gh` CLI's `gh issue edit --type` flag works on `gh >= 2.61.0`; fall back to GraphQL if the flag is rejected.

```bash
# Preferred: gh CLI flag
gh issue edit 12 --type "Bug"

# Fallback: GraphQL (need the issue's node ID + the org's IssueType node ID)
ISSUE_ID=$(gh api graphql -f query='
  query($owner:String!, $name:String!, $num:Int!) {
    repository(owner:$owner, name:$name) { issue(number:$num) { id } }
  }' -F owner="$OWNER" -F name="$NAME" -F num=12 --jq .data.repository.issue.id)

TYPE_ID=$(gh api graphql -f query='
  query($owner:String!, $name:String!) {
    repository(owner:$owner, name:$name) {
      issueTypes(first:20) { nodes { id name } }
    }
  }' -F owner="$OWNER" -F name="$NAME" \
  --jq '.data.repository.issueTypes.nodes[] | select(.name=="Bug") | .id')

gh api graphql -f query='
  mutation($issue:ID!, $type:ID!) {
    updateIssueIssueType(input:{issueId:$issue, issueTypeId:$type}) {
      issue { number issueType { name } }
    }
  }' -F issue="$ISSUE_ID" -F type="$TYPE_ID"
```

Cache the `issueTypes` lookup once per run — names → IDs do not change between issues in the same repo.

If the repo has **no Issue Types defined yet** (`issueTypes.nodes` is empty), the org admin must enable them in repo settings → Issues → Types. Print a one-line warning and skip Type assignment for that run — do not abort the rest of the pipeline.

### Print the classification

Before applying, print one compact line per issue:

```

#7   Feature  Add --json output flag
#9   Task     Bump pyyaml to 6.0.2
```

So the user can spot misclassifications before they hit GitHub.

## Dependency extraction

Build a set of edges `(child, parent)` meaning *child depends on parent* / *parent must ship before child*. Three sources, applied in order; later sources only **add** edges, never remove:

### 1. Body-text parsing (highest confidence)

Scan each issue body for these patterns. Case-insensitive. Edge goes `(this_issue, #N)`:

- `depends on #N`, `depends-on #N`, `dependency: #N`
- `blocked by #N`, `blocked-by #N`, `blocks-on #N`, `requires #N`, `needs #N`, `needs: #N`
- GitHub task-list checkboxes that reference issues: `- [ ] #N` is a sub-task; treat as *this depends on N*.
- Traditional Chinese / common bilingual phrasings: `依賴 #N`, `相依 #N`, `需要 #N`, `等待 #N`

Ignore the **reverse** direction (`blocks #N`, `closes #N`, `fixes #N`) — those describe what the issue resolves, not what it waits for. Do not invert them into edges.

### 2. GitHub native sub-issue / tracked-by graph

GitHub now has first-class sub-issue links surfaced through GraphQL. Run:

```bash
gh api graphql -f query='
  query($owner:String!, $name:String!, $cursor:String) {
    repository(owner:$owner, name:$name) {
      issues(first:100, after:$cursor, states:OPEN) {
        pageInfo { hasNextPage endCursor }
        nodes {
          number
          trackedIssues(first:50)   { nodes { number } }
          trackedInIssues(first:50) { nodes { number } }
        }
      }
    }
  }' -F owner="$OWNER" -F name="$NAME"
```

Paginate via `endCursor` until `hasNextPage` is false. For each issue `N`:

- Every entry in `trackedIssues` is a **sub-issue** of `N` → edge `(N, sub)` (parent depends on its sub-tasks).
- `trackedInIssues` is the inverse — you can derive the same edge from the other side. Use it only as a consistency check; don't double-add.

If the GraphQL call fails (older GitHub Enterprise, missing scope), log a one-line warning and continue without these edges. Do not abort the whole pipeline.

### 3. Semantic inference (you, the assistant, do this)

After the deterministic sources are collected, look at the remaining issues yourself. Read each title + first ~200 chars of body. Add an edge **only** when the dependency is concrete and obvious — e.g.:

- "Refactor X into a module" plainly enables "Add Y feature on top of X module" → edge.
- Two unrelated bug fixes → no edge, even if they touch nearby files.

Be conservative. False edges push issues unnecessarily late; missing edges only mean parallel work. **When in doubt, don't add the edge.** Print the inferred edges (with one-line reasoning each) before passing them into the planner so the user can see what you assumed.

If you find a cycle while adding semantic edges, drop the weakest inferred edge that closes the cycle. Body-parsed and GraphQL edges are never dropped — if those cycle, stop and report.

## Planning

Write the issue list and edges to a JSON file, then call the helper:

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/skills/issue-milestone-planner/scripts/plan_milestones.py" \
  --current-version "$CURRENT_VERSION" \
  --cap 20 \
  --input /tmp/imp-plan-input.json \
  --output /tmp/imp-plan-output.json
```

Input JSON shape:

```json
{
  "issues": [{"number": 12, "title": "..."}, ...],
  "edges": [[child, parent], ...]
}
```

Output JSON shape:

```json
{
  "milestones": [
    {"title": "v1.2", "issues": [3, 7, 12]},
    {"title": "v1.3", "issues": [5, 9]}
  ],
  "skipped": [{"number": 18, "reason": "cycle"}]
}
```

The cap defaults to **20 issues per milestone** (user's choice — adjustable via the `--cap` flag or if the user says "make the milestones bigger / smaller"). Overflow rolls forward: if v1.2 fills up, depth-0 issues spill into v1.3, and their dependents shift to v1.4 etc. The script enforces "depends-on lands in a strictly earlier milestone" — that invariant is non-negotiable.

## Execution

Print the plan as a compact table first (include the Type column so the user can sanity-check classification at the same time):

```
v1.2  (5 issues)
  #12  Bug      Refactor config loader crashes on empty TOML
  #7   Feature  Add --json output flag
  ...
v1.3  (3 issues)
  #9   Task     Bump pyyaml to 6.0.2
  ...
v1.4  (1 issue)
  #4   Task     Document new feature
```

Then create each milestone, assign its issues, **and apply the chosen Type to each issue**. Existing milestones with the same title should be reused — do not error out. Type assignments are also idempotent — re-applying the same Type is a no-op.

```bash
# Create (or reuse) milestone
EXISTING=$(gh api "repos/$REPO/milestones?state=open" --jq ".[] | select(.title==\"v1.2\") | .number")
if [ -z "$EXISTING" ]; then
  NUMBER=$(gh api "repos/$REPO/milestones" -f title="v1.2" -f state=open --jq .number)
else
  NUMBER="$EXISTING"
fi

# Assign milestone + Type in the same edit when possible
gh issue edit 12 --milestone "v1.2" --type "Bug"
gh issue edit 7  --milestone "v1.2" --type "Feature"
```

`gh issue edit --milestone` accepts the milestone **title**, not number — pass `"v1.2"` directly. `--type` accepts the Type **name** (`Bug` / `Feature` / `Task`). If `--type` is rejected (older `gh`), use the GraphQL fallback shown in *Issue Type classification*. Run the edits sequentially; parallel edits sometimes race against GitHub's rate limit.

After every milestone is processed, print a final one-line summary: `Created 3 milestones, assigned 9 issues, set 9 types (4 Bug / 3 Feature / 2 Task).` Done.

## Edge cases worth thinking through

- **Closed dependencies.** If a body says `depends on #45` and #45 is closed, drop the edge (the dependency is already satisfied).
- **Cross-repo references.** `owner/repo#N` references point outside this repo — ignore them.
- **Issue with N>10 dependencies forming a long chain.** Topological depth determines milestone, so a 10-level chain produces 10 milestones. That is correct, not a bug. If the user is surprised, the right fix is removing artificial dependencies, not capping milestone count.
- **Existing milestones from prior runs.** Reuse them by title match. The script's output will still list them.
- **Re-runs.** Idempotent: re-running with the same inputs produces the same plan and `gh issue edit --milestone X` on an issue already in X is a no-op.

## What NOT to do

- Don't write directly to `.github/` or commit anything — the planner only touches GitHub via the API.
- Don't fall back to plain `1.2` formatting; the user picked `v1.2`.
- Don't ask the user to confirm each milestone — they explicitly chose full automation. The single confirmation point is when the version can't be detected or when a hard cycle exists.
- Don't invent dependencies to "balance" milestone sizes. Empty later milestones are fine; over-eager edges destroy the actual schedule.
